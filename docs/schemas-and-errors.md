# Schemas and errors

Schema arguments may be Pydantic models, dataclasses, ordinary Python types,
`typing` constructs or raw JSON Schema dictionaries. Providers turn them into
OpenAPI components while the document is built.

## Supported schema values

With the `pydantic` extra installed, you can use:

- Pydantic 2 models;
- standard and Pydantic dataclasses;
- types accepted by `TypeAdapter`, such as `list[UserDTO]`,
  `Optional[int]` and `Literal['active', 'disabled']`;
- a ready `TypeAdapter` instance.

The built-in provider, which does not require Pydantic, supports common scalar
types, enums, collections and unions. A raw JSON Schema dictionary is always
accepted.

Use `markers.Ref()` to refer to a Python type from inside a raw schema:

```python
from qstd_openapi import markers

page_schema = {
    'type': 'object',
    'properties': {
        'items': {
            'type': 'array',
            'items': markers.Ref(UserDTO),
        },
    },
}
```

Pydantic 1.10 and models imported from `pydantic.v1` are supported through the
experimental `pydantic-v1` extra.

## Validation and serialization modes

Request bodies and parameters use a validation schema. Responses, errors and
webhooks use a serialization schema. When those schemas differ, components are
named `Model-Input` and `Model-Output`.

Field aliases are enabled by default. If the application serializes fields by
attribute name, configure the provider explicitly:

```python
from qstd_openapi import OpenAPI
from qstd_openapi.pydantic import PydanticSchemas

spec = OpenAPI(
    info={'title': 'Users API', 'version': '1.0.0'},
    schemas=[PydanticSchemas(by_alias=False)],
)
```

## Match the actual serializer

The response schema must describe what the application sends, not merely what
Pydantic would produce. Use `type_overrides` when a custom encoder changes a
type:

```python
from datetime import datetime
from decimal import Decimal

from qstd_openapi import OpenAPI, TypeOverride

spec = OpenAPI(
    info={'title': 'Users API', 'version': '1.0.0'},
    type_overrides={
        datetime: {'type': 'integer', 'description': 'Unix timestamp'},
        Decimal: TypeOverride(
            {'type': 'number'},
            mode='serialization',
            within='dataclasses',
        ),
    },
)
```

`mode` may be `validation` or `serialization`. `within` may restrict an
override to fields of Pydantic models or dataclasses. A list of overrides for
one type is checked in order, and the first applicable one wins.

FastAPI creates its own schemas before qstd-openapi merges the document.
`type_overrides` therefore does not alter a schema generated by FastAPI itself.
If both sides describe one component differently, the merge reports a
component conflict.

## Application errors

`openapi.errors()` does not prescribe an exception hierarchy. An error
provider converts the objects passed to it into an HTTP status and a schema.

`AppErrors` is the included provider for exception classes with an integer
code, a message and annotated payload fields:

```python
from qstd_openapi import OpenAPI
from qstd_openapi.contrib.app_errors import AppErrors


class ApplicationError(Exception):
    code: int
    message: str
    status_code = 500


class UserAlreadyExistsError(ApplicationError):
    """A user with this email is already registered."""

    code = 1001
    message = 'User already exists'
    status_code = 409
    email: str


spec = OpenAPI(
    info={'title': 'Users API', 'version': '1.0.0'},
    errors=[AppErrors(ApplicationError)],
)
```

The response schema is equivalent to:

```json
{
  "code": 1001,
  "error": "UserAlreadyExistsError",
  "message": "User already exists",
  "email": "user@example.com"
}
```

Attach the error to an operation:

```python
@openapi.errors(UserAlreadyExistsError)
async def register_user(request):
    ...
```

Several errors with the same status are combined with `oneOf`. Each error
schema is placed in `components/schemas`.

## Status and message rules

`AppErrors` resolves the HTTP status in this order:

1. the `status=` callable passed to the provider;
2. the exception class attribute named by `status_attr` (`status_code` by
   default);
3. the nearest matching base class in `status_by_class`;
4. `default_status`.

Reuse the same status function as the application's exception handler when
possible. This keeps the runtime response and the document aligned.

A constant class-level message becomes a JSON Schema `const`. A missing
message or a template containing `{` remains an unrestricted string. Set
`__openapi_message__ = 'dynamic'` or `'const'` to override that detection.

## Payload fields

Every public annotated attribute is included in the payload. Names starting
with `_`, `ClassVar` annotations and the built-in code/message/status fields
are skipped:

```python
class UserAlreadyExistsError(ApplicationError):
    code = 1001
    message = 'User already exists'
    email: str
    _origin: Optional[Exception] = None
```

Here `email` is documented and `_origin` is not. A public field whose type no
schema provider understands fails the build with the exception class and field
name in the message.

To change the convention, subclass `AppErrors` and override `status_for()`,
`payload_fields()`, `code_schema()`, `message_schema()` or `schema_for()`.
For a completely different error representation, implement `ErrorProvider`.
